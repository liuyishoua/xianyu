# 手机验证码续登

纯 HTTP 引擎也使用私有配置中的 `browser_proxy` 本机网络入口。SOCKS 使用
`socks5h`，域名解析与请求均通过同一出口，关闭环境变量代理覆盖；网络失败不回退直连。
发码成功后保存该请求的网络配置，验证码确认继续使用同一出口，即使全局配置已改变。
这是对现有网页短信接口的调用，不等同于取得开放平台应用权限，也不表示真实发码已经成功。

2026-10-14：纯 HTTP 实现补齐与浏览器相同的本机 SOCKS 出口，补齐运行环境
PySocks 依赖，发码及确认固定同一网络配置。通过正常维护队列冷却后做一次真实发码：
HTTP 200，响应根字段 `data`、`ret`，要求安全验证，未取得 `smsToken`。
因此同一网络出口不足以让当前请求正常发码，尚未定位与主人正常浏览器的具体差异。
该请求未进入短信等待或登录确认，不能宣告无人操作续登完成。

进一步在官方页面拦截发码（没有实际发送短信），比较字段名发现纯 HTTP 表单写成了
`navLanguage`，官方使用 `navlanguage`，现已纠正。纯 HTTP 表单还缺少官方运行时生成的
`ua`、`bx-ua`、`bx-umidtoken`、`pageTraceId` 等字段。该对照仍是在服务器浏览器中完成，
没有采集主人 Mac 上成功发码的请求，不能据此确定真实验证触发原因。

账号中心的短信续登可以选择正常 Chromium 浏览器执行官方手机登录页。
官方页面：<https://passport.goofish.com/mini_login.htm?appName=xianyu&appEntrance=web&fromSite=77&qrCodeFirst=false>。
页面使用的官方客户端脚本：<https://x.alicdn.com/vip/havana-nlogin/0.10.37/index.js>。

2026-10-13 对照官方脚本和实际浏览器发码请求：除了手机号、地区码和页面会话，

仅凭这个差异不能断言具体账号发码失败的原因；必须观察官方实际返回。

## 启用

安装可选依赖及 Chromium：

```bash
.venv/bin/python -m pip install -r requirements-sms-browser.txt
.venv/bin/python -m playwright install chromium
```

在真实工作台数据目录 `.local/web/phone-login-config.json` 保存：

```json
{"engine":"browser"}
```

若使用已有 Chrome，可额外设置 `browser_executable` 为实际浏览器可执行文件的绝对路径。
重启 `xianyu-web.service` 后生效。未配置时仍使用原来的 requests 引擎。

支持 `entry: "home"` 从官方首页的登录框进入，以及 `headless: false` 运行带窗口的普通 Chrome。
服务器没有桌面显示时，此模式使用已安装的 Xvfb 创建临时显示；不修改浏览器自动化标志或伪造安全参数。
新请求独立运行，等待验证码所需的 Cookie 与存储状态保存在原工作台。

可选 `browser_proxy: "socks5://127.0.0.1:18890"` 复用已配置的本机家庭网络入口。
只接受无凭据的回环代理；浏览器启动与后续请求不在代理失败时改成直连。
发码保存原网络配置，验证码确认和会话交接仍使用该配置，即使运行配置已更改。
不修改已有隧道服务、系统路由或其他应用的网络设置。
从官方短信页直接进入可设置 `entry: "login"`。
SDK 就绪采用定时轮询并最多等待 10 秒，避免输入框出现后安全脚本尚未初始化就发码。

`interactive: true` 启用保留会话的官方浏览器：发码遇安全验证时不关闭窗口，
原会话最多保留 30 分钟，账号矩阵会出现「短信验证」。此入口只允许已认证工作台用户查看
官方页面并用鼠标完成验证，不自动解决滑块，不接受任意脚本或导航命令。
截图使用不缓存的认证接口；窗口坐标有限制，取消原任务或修改绑定后停止操作。
原请求在验证码发出前保持未确认状态，不另发验证码；官方页面完成验证并实际返回 `smsToken`
后，才将同一个维护请求转为等待验证码。验证码由手机转发器送达后在原页面填写、点击登录，
不重新启动浏览器。只在官方成功响应、原 UID 和消息连接均核验通过后恢复监听。
会话结束清理浏览器引用与待处理输入；服务重启后不会凭旧标记自动再次发码或提交验证码。
本模式使用同机账号中心的持久化 SDK，依赖随 `requirements-sms-browser.txt` 安装。

## 流程及边界

1. 账号中心持久化发码意图，按原绑定手机号向闲鱼工作台发起请求。
2. 浏览器打开官方短信页面，填写手机号，通过页面按钮发码。
3. 官方返回 `smsToken` 才进入等待验证码；页面会话及 Cookie 只保存在本地工作台私有文件。
4. 手机转发器按已有签名、来源与任务去重逻辑提交验证码。
5. 验证码确认恢复原浏览器会话，由官方页面正常请求机制提交短信登录。
6. 只接受官方会话跳转，并核对原 UID；随后核验消息凭证，再恢复已开启的监听。

发码安全验证交给官方页面处理，不自动完成滑块；频率限制及其他错误显示脱敏原因。
发码响应不确定不会另发一次，验证码确认响应不确定不会重复提交。
切换引擎后已有等待任务仍沿用其原引擎。模拟测试通过不代表真实短信登录通过。

## 接回本机已完成的网页登录

工作台账号矩阵中的「接回网页登录」可以接收用户在官方网页完成短信登录后的 Cookie 请求头。
用户在浏览器 Network 面板中复制发往 `h5api.m.goofish.com` 的完整 Cookie 值，
直接粘贴到已认证工作台的密码输入框，不通过聊天或日志传递。
提交到 `POST /api/accounts/<uid>/browser-session`，使用既有登录及同源校验。

账号身份必须与指定原 UID 一致；登录态先在私有临时目录核验消息凭证，
失败则清理临时文件并保留原登录态。通过后才保存到原账号，重新检查连接，
并让原来启用的监听开始重连；停用的监听及其他账号保持原状态。
消息连接再次检查未通过时只报告登录态已保存，不宣告监听恢复。
原始 Cookie 不写入任务、审计记录或接口响应，临时目录在操作结束时删除。

这是本机网页登录的人工交接入口，不代表服务器自动发码或自动短信续登已验证通过。
